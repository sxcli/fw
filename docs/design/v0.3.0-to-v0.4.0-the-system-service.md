# v0.3.0 → v0.4.0 — the system service: the core's facilities become a cataloged member

> **STATUS (2026-07-28) — IMPLEMENTED (Y1-Y5, fw bf97cd5..dc6928c,
> vet f5cd3d6, completion 17d1fc1), with one design refinement over
> the text below:** `system.System` became an **interface**, not a
> struct — fw registers a private `systemService` implementing it, so
> no public wiring seam exists at all (the `Wire` idea died in
> review). Auto-admission landed as `Descriptor.Core` + an
> unexported `core()` chain method (unforgeable). The introspection
> view the facade returns is environment-blind by construction.
> `IntrospectionID`/`IntrospectionAlias` retired in favor of
> `system.ID`/`SystemAlias`. All Open items below were settled at
> implementation except view-scoping (still a recorded possibility).

## What we want to change

1. A new declarations-only package, **`sxcli.dev/fw/system`**: the
   `Introspector` **interface** (what today's concrete
   `*fw.Introspector` answers: applets, services, arguments,
   describe), the `System` facade type, and the `ID` constant. The
   package imports nothing of fw — pure vocabulary.
2. **`fw.init()` registers the System service** through the ordinary
   registration chain, with `system.ID` and the `*system.System`
   concrete type. Presence in every binary is guaranteed by the one
   import that makes a binary an fw binary — fw itself; the
   dependency arrow is `fw → fw/system`, no cycle, no blank-import
   magic. Init registering another package's type is init's ordinary
   right.
3. **The facade, not a service per facility.** `System` exposes the
   core's facilities as methods returning interfaces —
   `Introspector() system.Introspector` first, future facilities
   (runtime information, listing data, possibly closure-scoped
   introspection VIEWS) as further methods. Deliberately a mini
   service-locator for a closed, framework-owned set: one stable
   graph member forever, no per-facility admission questions, no
   dependency pollution with system services.
4. **Admission is the framework's.** `Build` auto-admits the core
   family regardless of `Accept` — stated in the spec as "core
   services are admitted by the framework, not the composition".
   `Accept` governs user services only.
5. **Deletions:** `run()`'s hand-registration of the Introspector;
   the "Introspector's concrete type is reserved for the core"
   squat-check (the service itself now holds the id and the concrete
   type — the ordinary duplicate-id and duplicate-concrete checks
   guard naturally).
6. **sxcli-vet:** the fw-root skip becomes surgical — in fw's own
   package, a chain that is *returned* is builder machinery (no
   fact, no verdict); a chain that reaches its terminal is a real
   registration (ordinary fact, ordinary checks). The System
   registration is then a normal member statically, and the
   core-synthesized-members gap (ledger #22) closes with zero
   analyzer knowledge of core magic.

## Why

- The Introspector is today registered by runtime code inside
  `run()` — invisible statically. sxcli-vet's per-root solving
  exposed the consequence: a dependency on `*fw.Introspector`
  (completion's applets) is unresolvable in the static model,
  because the member exists nowhere in source. Teaching the analyzer
  an implicit-members list would mirror a wart; registering the
  member like every other member removes the wart.
- The facade shape is chosen over per-facility services to keep the
  graph clean as the core grows ("I don't want to pollute the
  dependencies with 100 system services") and it opens the
  possibility of per-consumer Introspector views over the graph —
  no concrete use case yet, recorded as a possibility the shape
  permits.
- Interface returns end the concrete-type coupling: completion
  currently injects fw's concrete struct and had to hand-build its
  own narrowing seam (`engine.Source`) and fakes;
  `system.Introspector` is mockable by construction.
- The declarations/registration split (`fw/system` declares,
  `fw.init()` registers) resolves what neither pure home could: a
  subpackage alone cannot guarantee its init runs without an import
  cycle, and fw root alone would overload the already-crowded core
  naming. Split, both problems vanish.

## What we expect it to touch

- **New package `fw/system`**: interfaces + facade type + `ID`;
  no fw imports.
- **fw root**: `init()` registration; the runtime-wiring seam (the
  factory catalogs a shell; fw attaches the per-invocation runtime
  at startup — both halves framework-owned, the registration fully
  visible, the wiring an implementation detail); `run()`
  hand-registration and the squat-check removed; `Introspector`'s
  concrete API becomes the interface's implementation.
- **Builder**: core-family auto-admission.
- **completion**: migrates `I *fw.Introspector inject` →
  `system` vocabulary; its `engine.Source` may shrink to a type
  alias or die.
- **sxcli-vet**: the surgical skip (returned-chain rule); a fixture
  registering-and-injecting the System member; ledger #22 closed.
- **spec**: §4/§5 — the core-services-are-services statement, the
  admission rule, the facade contract.
- **Introspection identity**: `IntrospectionID` likely folds into
  `system.ID` — one member instead of a reserved id + skip-ejection
  history; the catalog/working-set design already removed the
  ejection special case, this removes the identity special case.

## Open (decide at implementation)

- The facade's exact method set at birth (`Introspector()` only, or
  also the `--applets` listing data as its own facility?).
- View-scoping: `Introspector()` returning a closure-bounded view
  per consumer — possibility recorded, no use case yet.
- The wiring seam's shape (where fw attaches the runtime to the
  shell — Build-time vs run-start).
- Whether `system.System` is injected by concrete type or the
  facade itself is also an interface.
