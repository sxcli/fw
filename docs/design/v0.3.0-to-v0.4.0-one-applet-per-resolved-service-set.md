# v0.3.0 → v0.4.0 — one applet per resolved service set, enforced at every door

## What we want to change

The day-one rule — exactly one applet is active per invocation —
becomes a HARD, checked invariant of the dependency graph, not a
side effect of dispatch. fw MUST check at **every place that can
introduce an applet into the graph**:

1. **Controls**: applets are not addressable by controls, period.
   The control flags resolve against the SERVICE view of the working
   set — which contains no applet: dormant ones are ejected and the
   root is not a service. Any applet reference in `--enable-id` /
   `--enable-alias` / `--disable-id` / `--disable-alias` /
   `--override`, active or dormant, reports plain "unknown
   service". Today's "applet %q is disabled" error disappears with
   the rule that made it possible.
2. **Dependency resolution — only the active applet provides
   interfaces to the graph.** Applets may declare `Provides`
   (unchanged at commit), but with the applet eject running before
   resolution, dormant applets are structurally invisible: a
   dependency naming a dormant applet's id is unresolvable, an
   interface dep never sees one as a candidate ("no registered
   service satisfies" when it was the only one). Services in the
   resolved service set may still resolve against the ROOT's interfaces — the
   sanctioned applet ↔ service channel.
3. **Backstop**: after resolution, the resolved service set MUST contain exactly
   one `Applet` — the dispatched one. Any other outcome is an
   internal error (a door we forgot), reported loudly, never
   silently tolerated.

Mechanism — **the catalog / working-set split**:

- **Catalog**: the Build result, immutable after Build. Dispatch,
  introspection/completion, `--applets` and `--upgrade-config` read
  it; nobody manipulates it.
- **Working set**: a per-invocation shallow descriptor copy.
  Immediately after dispatch, fw ejects every applet except the
  dispatched one from it; resolution then runs against a registry
  containing one applet **by construction** — controls and inject
  need no applet awareness, and `--enable-id`/`--enable-alias`
  naming a dormant applet reports plain "unknown service" (applets
  are not services from the operator's point of view). Cold-service
  ejection also operates on the working set.
- The "an introspecting resolved service set keeps the whole registry" special
  case (main.go:383) is REMOVED: it never guarded resolution
  (`Retain` runs after `plan`, so `expandDep` always saw the full
  registry), and under the split introspection needs data, not
  graph membership — queries answer names/schemas/ArgInfo from the
  catalog, never instances. Ejection becomes unconditional.
- `registry.Descriptor` gains an `Applet bool`, set by fw's
  registration commit (which already computes appletness); the
  registry and graph packages stay framework-ignorant — appletness
  is data.

Security note (intended channel, stated in the spec): a composed
service can observe the ACTIVE applet through interfaces the applet
chose to `Provides` — that is the sanctioned applet ↔ service
channel and the only one. Dormant applets are unreachable by
construction: not by interface, not by concrete type, not by id, in
any run including completion invocations. Explicit `Accept`
participation remains the trust boundary.

The doc paragraph that triggered this (a binary carries many
applets, exactly one is active, only its resolved service set is resolved) enters
the spec verbatim as the rule's statement.

## Why

- Documentation review (2026-07-20): the paragraph above was already
  written as truth and the code does not enforce it. Confirmed
  unguarded paths: `--enable <applet>` seeds any enabled descriptor
  with no applet test, and `expandDep` resolves dependencies against
  descriptors with no appletness filter (by concrete type or
  Provides).
- User-visible symptom: `mybox serve --enable grep` puts grep's
  config section into serve's argument schema and calls grep's
  `Configured()` — it never runs, so the failure is *silent*: the
  exact failure mode the composition release exists to eliminate.
- Root cause: the rule's enforcement lived in dispatch, which only
  guarantees the narrow reading (one applet *runs*). Applets are
  ordinary registry entries, the graph is framework-ignorant by
  design, and `--enable`/inject were written as generic service
  mechanisms — the resolved-service-set-level invariant fell between the layers'
  contracts. It was never a spec sentence, so it was never a test,
  so it never failed.
- Why every door AND a backstop, not one post-hoc check: per-door
  checks give the operator/author an error naming their action
  (the enable flag, the inject field); the backstop catches the
  doors we haven't imagined yet. Defense in depth for a hard rule.

## What we expect it to touch

- **internal/registry**: `Descriptor.Applet bool` (data only; no
  framework interfaces enter the package).
- **fw catalog commit**: sets the flag (already computes
  `isApplet`).
- **fw main.go**: the applet eject at the top of `execute` (dispatch
  is already structurally first, main.go:96 → 363); the
  skip-ejection-for-introspectors branch removed *(DONE 2026-07-29,
  ahead of this design: target-scoped introspection answers from the
  attach-time snapshot, so ejection is already uniform)*; `Retain` and
  resolution move to the working set; controls guard only against
  referencing the active applet.
- **internal/registry**: the catalog/working-set copy seam (Build
  already copies the catalog; the per-run copy is the new step).
- **internal/graph**: unchanged in spirit — with the eject before
  resolution it never sees a dormant applet; named-id deps on them
  fail as unresolvable, interface deps never see them as
  candidates. Post-resolution backstop in main.go after `Resolve`.
- **spec**: §4/§5 — the rule stated verbatim, the doors enumerated.
- **Tests**: one pin per door (enable-an-applet, override-to-applet,
  inject-by-type, inject-by-interface, inject-by-id) + backstop
  test; completion's per-keystroke planning inherits the guards
  (an `--enable <applet>` in the typed words makes the plan fail →
  fallback schema, worth one engine test).
- **sxcli-vet**: ledger rows — the inject-path checks are statically
  mirrorable (facts carry Provides + concrete identity + deps; vet
  knows appletness only if RegFact records it → RegFact gains an
  `Applet` field); the enable/override paths are runtime data,
  corpus-only. The mirror cannot know which applet dispatches
  (runtime selector), so graph-viability verdicts become
  per-candidate-root: check the composition once per applet as
  root, report only verdicts that hold for every root, else
  "cannot verify" naming the root-dependent cases.
- **Breaking**: any composition that (accidentally) depended on an
  applet or enabled one — loud now, silent before. v0.4.0.
