# v0.3.0 → v0.4.0 — the id=0 start gate

**STATUS: IMPLEMENTED 2026-09-11.** Rulings on the open points: only
`--help` serves at superuser (with a loud warning); everything else,
`--applets` included, refuses. The gate covers Windows too — an
elevated token, via the x/sys dependency the SCM handler already
carries — and the declaration is named `.AllowsSuperuser()` (the
"AllowsID0" spelling below is the historical proposal).

## What we want to change

1. At startup, before dispatch, fw checks the effective user id. If it
   is **0** and the dispatched applet has not declared that it accepts
   running as id 0, fw refuses to start — loudly, naming the applet.
2. An applet declares acceptance in its registration chain:
   `.AllowsID0()`. Absent = the default = refusal at id 0.
3. The check is `os.Geteuid() == 0`. On platforms without the concept
   (Windows), `Geteuid` returns -1, so the gate never fires — no
   applet needs to opt in there.
4. The refusal is a startup verdict through the normal failure road
   (exit non-zero, message on stderr), before any applet code runs.

## Why

- An applet written without id 0 in mind can be launched as id 0 by
  accident — a `sudo` habit, a cron entry, a service-manager unit with
  no user set. The default should be that this does not silently
  proceed: the program that never expected id 0 does not run at id 0
  unless its author said it may.
- Acceptance is the applet author's knowledge, not the operator's: the
  author knows whether the code path is written for id 0. So the
  declaration lives on the registration chain, not in the composition
  and not in a tag.
- "Never silent" applies: today the program just runs, and whatever it
  writes lands owned by id 0. The gate turns an implicit, invisible
  state into an explicit decision.

## What we expect it to touch

- **fw registration chain**: `.AllowsID0()` on `Registration[T]` and
  `NewBareRegistration`; a `Descriptor.AllowsID0 bool` (data), set at
  commit.
- **fw main.go**: the gate keyed on the dispatched applet.
- **platform seam**: a `geteuid func() int` runtime field defaulting
  to `os.Geteuid`, so the gate is testable without a real id 0;
  Windows returns -1 and the gate is inert.
- **spec**: §5 dispatch/lifecycle — the gate stated as a rule.
- **CHANGELOG**: behavior change (id-0 starts refuse by default).
- **Tests**: id-0-refuses-without-declaration,
  id-0-proceeds-with-`AllowsID0`, non-zero-id-unaffected.

## Open (decide at implementation)

- **Gate vs the serving surfaces.** Does `--help` / `--applets` /
  `--write-config` at id 0 refuse too, or only actual applet
  execution? Leaning execution-only — the gate guards running, not
  inspecting — but a `--write-config` at id 0 writes an id-0-owned
  file, which argues the other way.
- **Default verdict.** Refusal (the "never silent" reading, and v0 is
  free to break) versus a loud warning that proceeds. Leaning refusal.
