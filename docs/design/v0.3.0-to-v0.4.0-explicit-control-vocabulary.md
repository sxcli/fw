# v0.3.0 → v0.4.0 — explicit control vocabulary: `--enable-id`/`--enable-alias`, `--disable-id`/`--disable-alias`, `--override` id-only

## What we want to change

1. Four new core arguments replace the mixed-vocabulary pair:
   `--enable-id` / `--disable-id` take service **ids**,
   `--enable-alias` / `--disable-alias` take **aliases**. The flag
   names the vocabulary; the operator's intent is explicit in the
   command line itself.
2. Plain `--enable` / `--disable` are **removed**, not kept as sugar.
3. `--override from=to` keeps its shape and becomes **id-only on both
   sides**. The `from` side was always inherently an id — aliases
   never appear in dependency requests, so an alias there names
   nothing the resolver will ever ask for. The `to` side follows for
   consistency with the explicitness rule. An alias on either side is
   a violation, cleanly detectable now that the grammars are disjoint
   (see the disjoint-identities design).
4. **Applets are not addressable by controls.** The four flags and
   both `--override` sides resolve against the service view, which
   contains no applet (dormant ones are ejected before controls,
   and the root is not a service): any applet reference, active or
   dormant, reports plain "unknown service". No special cases —
   today's "applet %q is disabled" runtime error disappears with
   the rule that made it possible. The enforcement on the
   resolved-service-set side lives in the
   one-applet-per-resolved-service-set design; this rule is its
   control-surface face.
5. `resolveRef` is removed entirely: `-alias` flags are a byAlias map
   lookup, `-id` flags a registry lookup, `--override` sides validate
   as ids. The triple return, the tie branch and the caller `tied`
   plumbing all go with it.

## Why

- Review (point 5): the both-vocabularies-in-one-slot rule produced
  the alias/id tie, a clumsy triple-return resolver, and a first fix
  attempt that was a nil-deref bug. Explicit flags make the
  ambiguity inexpressible instead of handled.
- Override mechanics (verified in source): dependencies request ids —
  a by-interface dep resolves to a candidate's id, a by-id dep
  requests it literally — and `expandDep` passes every requested id
  through the override remap (`graph.go` `mapped`), re-checking that
  the substitute satisfies the field type. An alias on the `from`
  side could only ever be resolved *into* an id first; accepting it
  was convenience masquerading as capability.
- The flag names double as documentation: `--disable-alias console`
  reads as what it does, and completion can offer the right
  candidate set per flag (aliases for `-alias`, ids for `-id`)
  instead of a merged pool.

## What we expect it to touch

- **fw core**: `coreControls` grows the four fields (conf tags,
  usage texts); `controls()` in main.go — per-flag lookups against
  the service view replace `resolveRef`; `resolveRef` and its tests
  deleted; the "applet %q is disabled" dispatch-time error removed;
  graph `Controls` unchanged (already id-based).
- **Suppress vocabulary**: `FeatureDisable`/`FeatureEnable`
  equivalents follow the new names (both Feature vocabs).
- **completion**: `HintServiceID` splits into id- and alias-hinted
  candidate sets per flag; engine tests updated.
- **sxcli-vet**: ledger rows for the removed tie violation retire;
  new rows for alias-where-id-required on `--override` and for the
  controls-refuse-applets rule (runtime data — corpus-only).
- **spec**: §5 controls section rewritten; CHANGELOG entry (breaking
  operator surface — deployment scripts using `--enable`/`--disable`
  must move to the explicit forms).
- **Breaking**: operator-facing — v0.4.0.
