# v0.3.0 → v0.4.0 — short-argument priority

**STATUS: RATIFIED 2026-07-29 — NOT IMPLEMENTED**

## Background

An sxcli binary carries a catalog of services. Each invocation runs
one applet and computes its resolved service set: the applet plus every service it
transitively needs. Services declare command-line arguments on their
config struct fields: a long form (`--log-level`) and optionally a
one-character short form (`-l`). The framework core also declares
arguments, for example `--config` with short `-c`.

Long names are unique within a resolved service set; the framework checks that.
Shorts are not unique. Until this change, when two services in one
resolved service set declared the same short, the earlier-seated service silently
won it. Seating order is the composition order: services ranked by
the builder's `Order` call first, then the rest alphabetically by id.

## What we change

1. A short declared by two services in one resolved service set is an error.
   The old silent resolution is removed. (One service declaring the
   same short twice is already an error.)
2. The applet resolves the error by declaring a priority list on its
   registration: `ShortArgPriority("id1", "id2", ...)`. On a
   collision, the earlier id in the list wins the short. A listed
   service beats an unlisted one. A collision between two unlisted
   services stays an error. The loser keeps its long form.
3. Core shorts can't be won. A service declaring a short the core
   uses is an error, and `ShortArgPriority` can't change that.
4. An id that doesn't resolve to a service is ignored.

## Why

The old rule made short ownership depend on seating order. Adding a
service to a resolved service set can silently move a short to another field in
the next version of the binary. Making shorts globally unique  instead
was rejected: the alphabet is too short, collisions between 
independent services are inevitable. So a collision is an error and
the applet decides the winner, because the colliding arguments belong
to its invocation.

## What it touches

The project rule: sxcli-vet must do the same checks and produce the
same errors as the runtime. Checks are written once in the shared
`sxcli.dev/rules` module and both sides call them.

- **sxcli.dev/rules**: the one implementation. Input: the claimants
  (service id, short, core or not) in seating order and the applet's
  priority list. Output: the winner per short and the error bodies
  (unresolved collision, core short declared by a service).
- **conf engine**: the schema builder stops deciding shorts. It
  collects the claimants, calls the rules function and prefixes the
  returned bodies.
- **fw**: the `ShortArgPriority` chain method (commit checks it's on
  an applet), the catalog entry carries the list, the schema builder
  passes the active applet's list through. Completion reads the same
  schema builder and needs no changes.
- **sxcli-vet**: extracts the same facts from the source and calls
  the same rules function.
- **spec**: the short-collision policy becomes: within one service an
  error; across services an error unless the applet's list resolves
  it; core shorts reserved.
- **Tests**: the collision error, resolution by the list, listed
  beats unlisted, two unlisted still an error, core shorts, the
  non-applet error. The old first-come pins flip.
