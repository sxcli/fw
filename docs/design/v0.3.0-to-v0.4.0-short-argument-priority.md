# v0.3.0 → v0.4.0 — short-argument priority

**STATUS: RATIFIED 2026-09-11 — NOT IMPLEMENTED**
(supersedes the 2026-07-29 ratification, which placed the priority
list on the applet's registration; it now lives on the composition)

## Background

An sxcli binary carries a catalog of services. Each invocation runs
one applet and computes its resolved service set: the applet plus
every service it transitively needs. Services declare command-line
arguments on their config struct fields: a long form (`--log-level`)
and optionally a one-character short form (`-l`). The framework core
also declares arguments, for example `--config` with short `-c`.

Long names are unique within a resolved service set; the framework
checks that. Shorts are not unique. Until this change, when two
services in one resolved service set declared the same short, the
earlier-seated service silently won it. Seating order is the
composition order: services ranked by the builder's `Order` call
first, then the rest alphabetically by id.

## What we change

1. A short declared by two services in one resolved service set is an
   error. The old silent resolution is removed. (One service
   declaring the same short twice is already an error.)
2. The composition resolves the error by declaring one priority list
   on the builder: `Builder().ShortArgPriority("id1", "id2", ...)`.
   On a collision, a listed service beats an unlisted one; between
   two listed services the earlier id in the list wins. A collision
   between two unlisted services stays an error. The loser keeps its
   long form only.
3. The call is atomic and once-only, like `Order`: a second
   `ShortArgPriority` call is a violation. An id listed twice is a
   violation. An id naming no cataloged service is a violation (this
   changes the 2026-07-29 ruling, which ignored unknown ids — on the
   builder the list sits beside `Accept` and `Order`, which both
   refuse unknown ids, and a typo in a priority list must not
   silently un-resolve a collision).
4. Core shorts can't be won. A service declaring a short the core
   uses is an error, and `ShortArgPriority` can't change that.
5. Binaries without a builder call — `fw.Solo` and `fw.Main()` — have
   no priority list. A collision there is simply the error; the
   author of such a binary controls every registration and re-tags a
   field instead. The standalone conf door is untouched: one root
   struct cannot produce a cross-service collision.

## Why

The old rule made short ownership depend on seating order. Adding a
service to a resolved service set can silently move a short to
another field in the next version of the binary. Making shorts
globally unique instead was rejected: the alphabet is too short,
collisions between independent services are inevitable. So a
collision is an error and the composition decides the winner — the
composition owns the operator contract (the same principle behind
`Builder.Alias`), and one declaration covers every applet in the
binary instead of being repeated on each. A consequence: the same
two contenders resolve identically in every resolved service set
that carries both; a short cannot flip meaning between applets of
one binary.

## The static-readability convention

The project rule: sxcli-vet must do the same checks and produce the
same errors as the runtime — and for that it must be able to READ
the id lists. Ruled with this design, uniformly for the three
list-taking builder calls (`Accept`, `Order`, `ShortArgPriority`):
exactly two source shapes are legal.

1. A direct call whose every argument is a constant — exported ID
   constants (any package; constants cross package boundaries) or
   string literals.
2. A single spread of a single package-level variable declared in
   the SAME package as the call, whose initializer is a plain
   `[]string` composite literal of such constants:
   `var priority = []string{pkg1.ID, pkg2.ID}` …
   `ShortArgPriority(priority...)`.

Anything else — a variable from another package (var initializers do
not cross package boundaries), a computed element, an appended or
init()-assembled slice — is a vet violation with its own message, in
the same tier as the exported-id-constant and one-expression-chain
rules: source conventions vet alone enforces, because the runtime
never sees how a slice was assembled. Go's call syntax makes the two
shapes exhaustive (a spread cannot mix with other arguments), so
static judgment is complete for legal code — there is no
cannot-verify case.

## What it touches

Checks are written once in the shared `sxcli.dev/rules` module and
both sides call them.

- **sxcli.dev/rules**: the one implementation. Input: the claimants
  (service id, short, core or not) in seating order and the
  composition's priority list. Output: the winner per short and the
  violation bodies (unresolved collision, core short declared by a
  service, duplicate listing, unknown id, second call).
- **conf engine**: the schema builder stops deciding shorts. It
  collects the claimants, calls the rules function and prefixes the
  returned bodies.
- **fw**: the `AppBuilder.ShortArgPriority` method (recorded like
  `Order`, judged at Build), the App carries the list, the schema
  builder passes it through. Completion reads the same schema
  builder and needs no changes.
- **sxcli-vet**: a shared resolve-id-list helper (the two legal
  shapes above) feeding `Accept`, `Order` and `ShortArgPriority`
  alike; the composition mirror extracts the same facts and calls
  the same rules function.
- **spec**: the short-collision policy becomes: within one service
  an error; across services an error unless the composition's list
  resolves it; core shorts reserved.
- **Tests**: the collision error, resolution by the list, listed
  beats unlisted, two unlisted still an error, duplicate listing,
  unknown id, second call, core shorts, Solo-without-a-list, the
  var-spread convention (both legal shapes plus each illegal one).
  The old first-come pins flip.
