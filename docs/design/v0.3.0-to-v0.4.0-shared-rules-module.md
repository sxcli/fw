# v0.3.0 → v0.4.0 — sxcli.dev/rules: one implementation for everything fw and vet both validate

## What we want to change

A new, tiny, dependency-free module — working name `sxcli.dev/rules` —
holding every rule that fw enforces at runtime and vet enforces
statically. Both consume the same implementation; parity for these
rules becomes true **by construction**, and the corpus shrinks to
what genuinely cannot be shared. Not `misc`/`utils`: the module's
scope is exactly "the rules", and it stays dependency-free or it
dies.

### Tier 1 — string grammars (move verbatim, zero abstraction cost)

| Rule | Today (runtime) | Today (vet) |
|---|---|---|
| service-id grammar (incl. the new `/` floor) | fw `identity.go` + `internal/registry` copy | `tags.go` mirror (wrong vintage — audit #3) |
| alias grammar (sep-run/trailing-hyphen ban) | fw `identity.go` | `isValidAlias` (was stricter than runtime — audit #9) |
| separator-run ban | conf `engine.hasSepRun` + inline copy in fw `validAlias` | own copy |
| long/short argument grammar | conf `engine.isValidLong/isValidShort` | mirror |
| inject-tag grammar (`id[;optional]`, flags) | `internal/registry.parseInjectTag` | mirror |
| env-name derivation (`__` stitch, `_` fold) | conf `engine.deriveEnv` | needed by the future derived-collision check |

### Tier 2 — rule engines over a neutral field/type model

The tag matrix and chain shape are checked twice against two type
systems: conf's `extract` walks `reflect.StructField`s, vet's
`checkConfigStruct` walks `go/types`. Same rules, different
carriers. Shared shape: the rule core operates on a neutral
description — `FieldDesc{Name, JSONTag, ConfTag, EnvTag, PosTag,
DumpTag, Kind, Elem…}` and `StepDesc{From, InType, OutType}` (type
identity as opaque strings) — with two thin adapters: a reflect
adapter (conf engine) and a go/types adapter (vet). The rule
bodies — the whole matrix: json-name mandate, conf-top-level-only,
version purity, pos shape, per-level duplicates, unsupported
types — live once.

### Tier 3 — the composition solver

vet's graph mirror is already "pure string-set logic over declared
facts" because the runtime deliberately matches by DECLARED
`Provides`, not open-world satisfaction. That means the *solver* —
members in composed order, disable/enable/override application,
candidate pools, ranked-wins, unranked-tie verdicts, closure walk —
can be one implementation over `Member{ID, Applet, Provides,
Aliases, Ranked, Deps}`. fw's `internal/graph` keeps only the
runtime-specific rim (reflect satisfaction re-check, injection, SCC
ordering for lifecycle); vet's `RegService` facts feed the same
solver directly.

### Tier 4 — message bodies

Per the single-home-checks design, validators format the message
body once, callers add the owner prefix. The bodies for shared rules
live next to the rules — fw and vet emit identical text because they
call identical code.

**Note (open concern):** this sounds unsustainable as a long-term
model — string bodies scattered next to rules, prefix conventions,
and no translation story for any of it. We need to think of a better
way to collect errors altogether: structured violation records (rule
id + parameters, formatted at the reporting edge) would make
identical-by-construction trivial to prove, allow deferred
formatting, and even allow translation of operator-facing validation
errors — without forcing anything to be Configured on failure paths.
Not designed here; recorded so the Tier 4 shape is understood as
interim.

### Explicitly NOT shared

Instance-level facts (factory defaults — vet's composite-literal /
"cannot verify" tier), begins-with-actual-import-path (go/types
only), dispatch/runtime-data checks (controls, file contents),
conf's fill/apply machinery. These remain corpus territory.

## Why

- The parity mandate (spec §8): same checks, same errors. Yesterday
  proved mirrors drift: two id grammars diverged in both directions,
  alias grammar diverged, the tag mirror missed per-level rules the
  runtime had (vet audit #3, #5, #9). Every shared implementation
  converts a ledger row from "measured by corpus" to "true by
  construction".
- The single-home-checks design established one-implementation
  inside the repos; fw↔vet sharing is its cross-repo continuation
  and needs a home neither repo can be (fw's rules are internal; vet
  must not depend on fw).
- Precedent reversal acknowledged: utils was rejected when it was
  one type looking for a home; this module has a product identity —
  the rules — and the parity mandate as its reason to exist.

## What we expect it to touch

- **New repo** `sxcli-rules`, module `sxcli.dev/rules` (packages:
  `grammar`, `tags`, `chain`, `solve`; zero deps; joins the release
  train FIRST — everything else pins it).
- **conf**: engine's `extract` becomes the reflect adapter over
  `rules/tags`; grammar helpers re-export or call `rules/grammar`;
  `ValidateSteps` body moves to `rules/chain`.
- **fw**: `identity.go` and registry grammar delegate;
  `internal/graph` splits solver (shared) from injector/lifecycle
  (kept); message bodies from the shared rules.
- **sxcli-vet**: deletes its grammar and tag mirrors; writes the
  go/types adapter; feeds facts into `rules/solve`. The analyzers
  shrink to adapters + fact plumbing + the go/types-only checks.
- **Ordering**: this lands BEFORE piecemeal vet fixes — most of the
  vet audit's mirror-fidelity majors dissolve into "delete the
  mirror, use the rules".
- **Release**: rules v0.1.0 → conf v0.2.0 → fw v0.4.0 → vet v0.2.0,
  completion bump last.
